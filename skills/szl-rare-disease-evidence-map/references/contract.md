# Synthetic evidence-map contract v1

This contract is intentionally narrower than HPO and ClinVar. It tests provenance and disagreement handling without processing patients or making a medical conclusion. All three inputs are UTF-8 JSON objects, at most 256 KiB each; JSON duplicate keys, non-finite values, unknown fields, symlinks, and malformed types fail closed. The CLI reads only its three explicit paths, prints JSON to stdout, and writes no output file. Exit 0 means the synthetic map was built; exit 2 means input failure. Neither is clinical approval.

Before reading bytes, the reader checks that the opened descriptor is the same regular, non-reparse file it inspected. It bounds the read to the inspected size plus one byte and rejects observed identity, size or modification changes after the read. Native no-follow and nonblocking flags are used when available. These checks do not establish a hostile-filesystem sandbox. Synthetic declarations and restricted tokens also cannot authenticate that operator-supplied data were invented.

On CPython 3.12 for Windows, path `lstat` and descriptor `fstat` expose different ctime clocks. Their explicit birthtime values are compared across APIs; each API's ctime must remain unchanged before and after reading. Device, inode, mode, size and mtime checks remain intact. The dedicated Windows evidence-map CI job checks native compatibility; synthetic split-clock tests do not substitute for that run.

`assets/example-manifest.json` uses schema `szl.rare-disease-evidence-map.v1`, an opaque synthetic `exercise_id`, `synthetic: true`, and `sources.hpo` / `sources.clinvar` with exact `release` and `sha256` fields. The public `map_evidence(manifest_bytes, hpo_bytes, clinvar_bytes)` API parses and hashes the same raw bytes; its `EXACT_INPUT_BYTES` source binding requires each source digest and release to match the manifest. The CLI reads the three file byte streams and passes them to that API. Release strings must start with `SYNTHETIC-` and exactly match the release in the corresponding source. The report's manifest digest also hashes the supplied manifest bytes. This is a byte check of supplied local inputs, not an authenticated provider readback.

The HPO-shaped source uses schema `szl.synthetic-hpo.v1`, `synthetic: true`, `rights: SYNTHETIC_ONLY`, a release, and 1–256 `annotations`. Every annotation carries a `SYNTH-COND:` condition reference, a `SYNTH-HP:` term ID, a `SYNTH-REF:` provenance token, and a `qualifier` of `ANNOTATED` or `EXPLICIT_NEGATIVE_ANNOTATION`. The HPO-shaped source release binds the annotation snapshot and the interpretation of its term IDs; individual HPO-like term IDs do not have ClinVar-style accession versions. An explicit negative annotation is a present row with a term and source reference. Absence of any annotation row for a condition is missing evidence, not an explicit negative. Exact duplicate condition/term/qualifier/source-ref entries are rejected, while independent source references for the same annotation remain visible. There are no patient observations or text labels.

The ClinVar-shaped source uses schema `szl.synthetic-clinvar.v1`, the same synthetic and rights declarations, a release, and 1–256 `records`. Each record has a synthetic condition reference, versioned `SYNTH-VCV:` and `SYNTH-RCV:` references, and 1–16 `submissions`. A submission retains a versioned `SYNTH-SCV:` reference, a numeric `SYNTH-ASSERT:0001`-style opaque token, and a `SYNTH-REF:` provenance token. Duplicate RCV or SCV references are rejected. These deliberately nonclinical tokens do not encode benign/pathogenic categories and cannot be used to classify a variant.

The output groups by the union of condition references. It emits `DIVERGENT_DECLARED_TOKENS` only when two or more distinct submission tokens appear within one RCV record; a difference is a question for source review, not proof of clinical conflict. It emits `MISSING_HPO_ANNOTATION` or `MISSING_CLINVAR_RECORD` for one-sided links and never silently drops them. Every result has `readiness: HOLD` and explicit `NOT_AUTHENTICATED_PROVIDER_DATA` / `NOT_CLINICALLY_VALIDATED` limits.

For real-world interpretation, retain distinct ClinVar SCV, RCV and VCV scopes and accession versions: SCV is a submitted record, RCV aggregates variant-condition pairs, and VCV aggregates by variant. HPO's disease annotations carry evidence and provenance, but rights and source versions need independent checks. See the [ClinVar data model](https://www.ncbi.nlm.nih.gov/clinvar/docs/data_model/), [ClinVar identifiers](https://www.ncbi.nlm.nih.gov/clinvar/docs/identifiers/), and [HPO annotation format and OMIM reuse note](https://obophenotype.github.io/human-phenotype-ontology/annotations/phenotype_hpoa/). None of those real records are accepted by this helper.
